AIにコードを書いてもらった。説明も筋が通っている。テストも通った。それでも、実際に使うと動かない。

この経験がある人にこそ、pstackは役に立ちます。pstackは、AIに仕事を渡すときの手順を整える、開発用のスキル集です。目指すのは、コードの生成量を増やすことよりも、問題を理解し、適切な変更を加え、その変更が実際に機能するところまで確かめることです。

この記事では、最初にCursorへ導入し、小さな練習プロジェクトで一つの変更を完了させます。そのあと、実際のアプリに適用する方法、設計やレビューを深める方法、複数エージェントや長時間の作業へ広げる方法を説明します。

本ガイドは、Lauren Tan（@poteto）が公開している 公式pstack を扱います。

調査基準日は2026年9月12日。公式リポジトリのコミット 889ec4b68fa5aab0e867dad71ec3fdf386ae48f3、プラグイン版 0.15.2 に基づきます。以下のプロンプトは本記事の実践例です。画面名や利用可能なモデルは、使っているCursorの版・アカウントによって異なります。確認したプラグイン定義

1. まず覚えるのは /poteto-mode だけ

pstackにはさまざまなスキルがありますが、最初から全部覚える必要はありません。普段の開発では、Cursorのチャットで次のように依頼します。

入力・表示例
/poteto-mode 注文を再送すると通知が二重に届きます。
まず再現し、原因を特定して修正してください。
修正後は同じ手順で通知が1回だけ届くことを確認してください。

/poteto-mode は、依頼に合った作業手順を選ぶ入り口です。この例なら、不具合修正の手順を選び、再現、調査、修正、検証へと進みます。

ここで渡している情報は三つです。

  1. 起きていること：再送すると通知が二重に届く。
  2. してほしいこと：原因を特定して直す。
  3. 終わりの条件：同じ操作をしても通知が1回だけ届く。

「どのファイルを何行書き換えるか」まで人間が決めなくても、目的と確認方法が具体的なら、エージェントは調査を進められます。

実行中は、作業リストにも注目してください。pstackは選んだ手順をリストに展開します。省略する手順には理由を残す設計なので、何を調べ、何を省いたのかを追えます。ルーティングの公式ガイド

スキル、プレイブック、エージェントの違い

言葉 意味 pstackでの例
スキル 特定の仕事を進めるための指示と資料 /how、/architect
プレイブック 作業の種類に対応する一連の手順 不具合修正、性能改善、PRの監視
エージェント 実際に資料を読み、ツールを使い、作業するAI Cursorの親エージェントやサブエージェント
検証用ハーネス アプリを繰り返し操作・観測するための道具 ブラウザ操作、CLI実行、API呼び出しの仕組み

たとえば、「通知の不具合を直す」という依頼を受けたエージェントが、不具合修正プレイブックに従い、必要な場面で /how などのスキルを使います。

入力・表示例
あなたの依頼
    ↓
/poteto-mode が作業の種類を判断
    ↓
対応するプレイブック
    ↓
調査・設計・実装・検証のスキルと道具
    ↓
変更内容と、その変更が動く証拠

pstackを入れたからといって、アプリの起動環境や認証情報まで自動的に揃うわけではありません。「仕事の手順」と「実際に操作できる環境」の両方を用意することで効果が出ます。

2. 導入する前に、必要なものを揃える

最初の実践には、次のものを使います。

必要なもの 何に使うか
Cursorと、Agentを利用できるアカウント pstackを読み込み、作業を実行する
Git 変更前後の状態を記録する
作業するプロジェクト AIが読んだり変更したりする対象
そのプロジェクトの実行環境 変更後のプログラムを動かす

この記事の練習プロジェクトでは、実行環境としてPython 3.10以上を使います。Pythonはpstack自体の必須要件ではなく、教材の要件です。自分のアプリがNode.jsやGoで動くなら、そのアプリの環境を使います。

Cursorは 公式サイト から、Gitは 公式のインストール案内 から準備できます。Pythonがなければ Python公式サイト から導入してください。

「ターミナルに入力するもの」と「チャットに送るもの」を分ける

初めて使うときに混乱しやすい点です。

ターミナルで実行
git --version
python3 --version

これはターミナルで実行します。Cursorのターミナルでも構いません。

入力・表示例
/poteto-mode このコードの動きを説明してください。

こちらはCursorのAgentチャットへ送ります。ターミナルに /poteto-mode と打つものではありません。

以降も、シェルコマンドとチャット用プロンプトを区別して掲載します。Windowsで python3 が見つからずPython Launcherが使える場合は、教材の python3 を py -3 に読み替えてください。

料金について

pstackのソースはMITライセンスで公開されています。ただし、AIモデルやクラウド実行の利用料まで無料になるわけではありません。特に複数モデルの比較と長時間実行は、実行するエージェント数や試行回数が増えます。

最初は小さな一件で動きを把握し、Cursor側の利用量を確認してから広げましょう。固定の月額や「一回いくら」という数値は、モデルと契約、依頼内容で変わるため本記事では置きません。ライセンス・Cloud Agentsの料金説明

3. Cursorにpstackをインストールする

手順1：作業するフォルダをCursorで開く

すでにアプリがある人は、そのプロジェクトを開きます。練習用のプロジェクトを使う人は、次章のZIPを展開したフォルダを開いてください。

「pstackのソースコードが入ったフォルダ」ではなく、これから調査・変更したいプロジェクトを開くのが基本です。

手順2：チャットでインストールする

Cursorのチャットで入力します。

入力・表示例
/add-plugin pstack

候補が表示されたら、公開元が cursor/plugins、作者がLauren Tanのpstackであることを確認して追加します。名前だけで選ばず、公式READMEと照合してください。

GitHubで公開されているからといって、通常利用のために自分でリポジトリをcloneしてビルドする必要はありません。公式の導入手順は、このプラグイン追加です。セットアップガイド・Cursorのプラグイン説明

手順3：利用するモデルを設定する

続けて入力します。

入力・表示例
/setup-pstack

このスキルは、現在の環境で利用できるモデルを確認し、実装、調査、判断、レビューなどの役割ごとに割り当てます。

初心者は、モデル名をネット上の設定例からそのままコピーするより、検出された候補から選ぶほうが確実です。使えないモデルを設定すると、サブエージェントの起動で止まってしまいます。

設定時には、たとえば次の希望を伝えられます。

入力・表示例
まず小規模な作業で試します。
利用可能なモデルだけを使ってください。
各役割の設定と、レビュー時に何体起動するかを説明してください。
複数モデルを使う必要が薄い役割は親チャットのモデルを継承させたいです。

設定は ~/.cursor/rules/pstack-models.mdc に保存されます。~ はホームフォルダを表します。これはユーザー側のルールなので、プロジェクトのコードとは別の場所です。

auto と inherit-parent は、ここではどちらも「親チャットのモデルを継承する」という意味です。特定モデルの名前ではありません。また、レビュー用のモデル一覧は、項目数に応じてエージェントが起動します。同じ継承指定を複数並べても、一体になるわけではありません。setup-pstackの定義

手順4：必要に応じて補助プラグインを追加する

pstackの一部のワークフローは、別プラグイン cursor-team-kit のスキルを参照します。コード整理の /deslop、CLIやUI操作用の control-cli、control-ui などです。

公式が案内する一式で使う場合は、こちらも追加します。

入力・表示例
/add-plugin cursor-team-kit

これはpstackの別名ではなく、補助する道具のセットです。/create-skill や /loop のようにCursor側が提供する機能もあります。どの機能がpstackに入っていて、どの機能がホストや補助プラグインに属するのかを分けておくと、見つからないコマンドの原因を追いやすくなります。同梱されない依存機能

手順5：新しいチャットで確認する

モデル設定は新しいセッションに適用されるため、セットアップ後に新しいチャットを始めます。

最初の確認は、書き換えを伴わない依頼で十分です。

入力・表示例
/poteto-mode このプロジェクトの起動方法と、利用者が触る入り口を調べてください。
コードは変更しないでください。
どの資料・ファイルを根拠にしたか示し、日本語で説明してください。

スキルが認識され、実際のプロジェクトを読み、調査結果が返ってくれば、最初の準備はできています。依頼を読んだだけで「調べました」と返していないか、根拠のファイルも見ておきましょう。

4. 最初の実践：小さなCLIにJSON出力を追加する

いきなり本番アプリの大改修を任せるより、一件の変更を最後まで見届けるほうがpstackの使い方をつかめます。

ここでは、支出のCSVを読み込み、件数と合計を表示する小さなプログラムを使います。CLIとは、ターミナルから実行するプログラムのことです。

教材：pstack-first-project.zipをダウンロード

この教材は本記事用に作成したもので、pstack公式の配布物ではありません。追加パッケージや外部サービス、GitHubアカウントは不要です。

手順1：教材を開く

ZIPを展開し、pstack-first-project フォルダをCursorで開きます。中身は次のとおりです。

入力・表示例
pstack-first-project/
  report.py          集計プログラム
  test_report.py     既存の動作を確認するテスト
  expenses.csv       3件の支出
  empty.csv          見出しだけのCSV
  README.md          教材の使い方
  .gitignore         Gitに入れないファイルの指定

Cursorのターミナルを開き、次を実行します。

ターミナルで実行
python3 report.py expenses.csv

次の表示が出ます。

入力・表示例
件数: 3
合計: 3000円

続いて既存のテストを動かします。

ターミナルで実行
python3 -m unittest -v

2件のテストが通り、最後に OK が表示されれば準備完了です。この初期状態の実行と2件のテストは、記事作成時にも確認しています。

can't open file などが出る場合は、開いているフォルダやターミナルの現在地が違う可能性があります。report.py があるフォルダで実行してください。

手順2：変更前をGitに記録する

新しく展開した教材フォルダで、一度だけ次を実行します。

ターミナルで実行
git init -b main
git add report.py test_report.py expenses.csv empty.csv README.md .gitignore
git commit -m "chore: add pstack tutorial starter"
git switch -c practice/json-output

最初の3行は、教材の出発点を記録する操作です。最後の1行は、練習用のブランチを作って移動します。ブランチは、元の履歴から分かれて変更を積み重ねる場所です。

Gitに名前とメールアドレスを求められた場合は、自分の情報を設定してから git commit をやり直します。設定は教材リポジトリだけに限定できます。

ターミナルで実行
git config user.name "自分の名前"
git config user.email "自分のメールアドレス"

引用符の中は自分の情報に置き換えてください。すでにGit管理されている実プロジェクトでは、この初期化手順を繰り返す必要はありません。

手順3：目的と完了条件を送る

Cursorのチャットに次を送ります。

入力・表示例
/poteto-mode report.py に --json オプションを追加してください。

--json なしの出力は既存と完全に同じにしてください。
--json ありでは、標準出力を count と total_yen だけのJSONオブジェクトにします。
expenses.csv は count=3、total_yen=3000、empty.csv は両方0です。
数値は文字列でなく整数にしてください。

元の出力を変更前に保存し、既存テストと実際のCLI実行で前後を比較してください。
JSONはパーサーで読み込み、値まで検証してください。

これはローカル演習です。現在の練習ブランチで作業し、commitは可能です。
push、PR作成、merge、公開は行わず、検証結果を示して終了してください。
追加パッケージは使わず、解説は日本語でお願いします。

JSONは、ほかのプログラムが扱いやすいデータ形式です。今回ほしい出力は、意味としては次のものです。

JSONの例
{"count": 3, "total_yen": 3000}

空白の置き方ではなく、JSONとして読み込めること、キーと値が正しいことが重要です。上のJSONは追加したい仕様の例であり、教材に最初から実装済みの出力ではありません。

このプロンプトで公開しないことを明記したのは、pstackの変更系プレイブックにはPR作成まで進む手順があるためです。今回は学習用なので、ローカルで完結するよう範囲を指定しています。

手順4：結果を確認する

変更後、エージェントには少なくとも次を実行してもらいます。自分でも同じコマンドを試せます。

ターミナルで実行
python3 report.py expenses.csv
python3 report.py expenses.csv --json
python3 report.py empty.csv --json
python3 -m unittest -v

確認するのは、次の三点です。

確認項目 合格の条件
既存の表示 件数3、合計3000円。改行を含めて元と同じ
JSON出力 パーサーで読め、整数の count と total_yen が正しい
空のデータ 見出しだけのCSVで件数・合計がともに0

「テストを追加しました」で終わらず、実際のCLIの実行結果まで確認します。JSONについても、「エラーなく読み込めた」だけでは足りません。値が全部0でも読み込みは成功するため、期待する値との照合が必要です。

さらに差分を見たい場合は、ターミナルで次を実行します。

ターミナルで実行
git diff main
git status --short

エージェントがすでにcommitしていても、git diff main なら出発点からの変更を確認できます。

手順5：自分が説明できる状態にする

最後に、次を送ってみてください。

入力・表示例
/teach 今回の変更を、Python初心者にもわかるように説明してください。
引数の受け取り、集計、出力の切り替えがどうつながるか知りたいです。
通常出力を壊していないと判断できる根拠も示してください。

ここまでできれば、最初の一周は完了です。AIに変更を頼み、実行結果で確かめ、変更を理解するところまで進められました。

5. 依頼文は「目的・制約・証拠」で組み立てる

pstackへの依頼は長ければよいわけではありません。次の形で考えると、必要な情報が揃います。

入力・表示例
/poteto-mode ［何を実現したいか］。
［守ってほしい制約］。
［どの操作・結果で完了と判断するか］。
［どこまで実行してよいか］。

たとえば、次の依頼は終わりが曖昧です。

入力・表示例
/poteto-mode 設定画面を使いやすくしてください。

次のようにすると、観測できる結果に変わります。

入力・表示例
/poteto-mode 設定画面に検索を追加してください。
設定項目の表示名で絞り込み、検索を消すと全項目に戻るようにします。
既存の保存処理は変更しないでください。
実際の画面で検索、検索解除、設定保存、再読み込みを確認してください。

「使いやすい」を、検索できる、戻せる、保存できる、再読み込み後も保たれる、という確認可能な挙動に分解しています。

対話が続いているときは短くてよい

/poteto-mode は、その会話で継続するモードとして定義されています。すでに目的と条件が共有されていれば、「続けて」「その方針で実装して」で足ります。

話題を変えるときは、切り替えを明示します。

入力・表示例
/poteto-mode new task.
ログアウト後もキャッシュが残る理由を調べてください。
今回は調査だけで、修正はしないでください。

以前の実装作業の続きとして解釈されないようにするためです。モードを終えたいときも、「この会話ではpoteto-modeを解除してください」と伝えられます。会話の継続と切り替え

手順を細かく書きすぎない

毎回 /how → /why → /architect → /arena のように全部指定すると、依頼に適したプレイブックの順序と食い違うことがあります。

基本は目的と制約を渡し、特定の判断を変えたいときだけスキル名を指定します。たとえば「設計を見てから実装してほしい」なら、次のようにします。

入力・表示例
/architect with checkpoint.
CSVのインポート機能を設計してください。
設計案と利用側のコード例を見せ、実装前に止まってください。

/architect は通常、設計から実装まで進むため、設計だけ見たい場合にはチェックポイントを明記するのが重要です。設計の公式ガイド

6. 本格運用の土台：アプリ専用の検証スキルを作る

ここからがpstackを継続的に使ううえでの中心です。

あるエージェントが頑張ってアプリの起動方法を見つけても、次のエージェントがまたゼロから調べるのでは、毎回同じ時間がかかります。ログイン方法、データの準備、画面への移動も同じです。

そこで、アプリを起動し、操作し、結果を確かめる手順を、プロジェクト専用のスキルとして残します。

テストと実動作の検証を組み合わせる

テストには、特定の条件を素早く繰り返し確認できる利点があります。一方、実際のアプリでは、設定、認証、保存、表示などの組み合わせで問題が起きます。

変更 実際に確かめたいこと
CLIの新オプション 利用者が打つコマンドで正しい出力になる
保存ボタン ボタンを押すと保存され、再表示しても残る
API リクエストに対する応答と、必要なデータ更新が正しい
性能改善 同じ条件で、変更前後の処理時間や負荷が改善する
移行処理 実データに相当する入力を読み、期待どおりの出力になる

ビルド、単体テスト、実動作の確認は、それぞれ違う証拠です。一つで全部を代表させず、変更の種類に合うものを選びます。検証の公式ガイド

生成コマンドを実行する

自分のアプリをCursorで開き、チャットで入力します。

入力・表示例
/create-verification-skill

スキルはまず、プロジェクトから次の情報を調べます。

  1. 利用者が触るのは、Web画面、CLI、APIなどのどれか。
  2. アプリをどう起動し、起動完了をどう確認するか。
  3. 既存のテストや操作用ツールを利用できるか。
  4. 結果を何で観測できるか。
  5. 複数の検証を同時に走らせても、データやポートが衝突しないか。

コードからわからない認証方法などは、そこで補足します。既存の操作用ハーネスがある場合は、それを優先する定義になっています。すでにある仕組みを捨てて、別のものを作り直す必要はありません。生成スキルの定義

練習プロジェクトで試すなら、次のように範囲を伝えます。

入力・表示例
/create-verification-skill
この支出集計CLI向けに作ってください。
通常出力とJSON出力を、実際のコマンド実行で確認できるようにします。
ローカル教材なのでpushやPR作成は不要です。
生成した手順を一度実行し、後片付け後にも証拠が残ることを確認してください。

何が生成されるのか

基本の保存先は次の形です。<app> の部分はプロジェクトに応じて決まります。

入力・表示例
.cursor/skills/verify-<app>/
  SKILL.md
  features/
    README.md
    機能ごとの説明ファイル
  必要に応じた操作・検証用スクリプト

SKILL.md の中心は、次の五つです。

項目 書くこと
Launch 起動方法と、準備完了の見分け方
Doctor 操作してよい正常な環境かどうかの確認
Drive 実際の利用者の経路に沿った操作方法
Evidence 何を証拠として、どこへ保存するか
Cleanup 自分が起動したものや一時データの後片付け

Doctorは、たとえば「指定ポートのアプリが起動している」「想定する版である」「テストユーザーでログインできる」を確かめる入口です。違う環境を操作して得た結果を、成功の証拠にしないためにあります。

また、生成しただけでは完成ではありません。現在の定義は、起動、Doctor、少なくとも一つの機能の操作、証拠保存、後片付けを一度通して実行することを求めます。最後に、保存した証拠がCleanupで消えていないことまで確認します。生成物と実証の要件

Feature Mapは「どこで何ができるか」の地図

Feature Mapは、ファイル名や関数名を並べた索引ではありません。利用者の視点で、機能への辿り方と確認すべき結果を示します。

たとえば「設定の保存」なら、次のような内容です。

知りたいこと 記載例
何の機能か 通知のオン・オフを保存する
どう辿り着くか 設定画面を開き、通知タブへ移動する
どう操作するか 通知設定を変更し、保存ボタンを押す
何が成功の証拠か 再読み込み後にも設定が維持される
注意点 テストアカウントが必要。権限によって項目が非表示になる

現在の生成定義では features/README.md を索引にし、各機能のファイルに Sub-features、How to get to it (user POV)、Driving it with <harness>、Gotchas という見出しを使います。添付の解説記事にある references/features という配置とは異なるため、実際の生成結果を基準にしてください。Feature Mapの公式例

/control-app は、全員が同じ名前で使えるコマンドではない

Lauren Tanの解説には /control-app という呼び出しが出てきます。これは、アプリ用に作られた検証スキルを表す例として読む必要があります。

自分の環境では、生成された SKILL.md の name とCursorの候補に出る名前を確認します。たとえば verify-expense-report という名前で生成された場合に、そのスキルを呼び出します。スキル名を確認する前に、記事中の例を固定コマンドだと思わないことが大切です。

7. 検証スキルを育てる：作って終わりにしない

アプリの画面や操作方法が変われば、検証手順も古くなります。その状態を放置すると、AIは「存在しないボタンを押そうとする」「新機能を一度も検証しない」といった問題を起こします。

更新には次を使います。

入力・表示例
/maintain-verification-skill

このスキルは、機能ごとのソース調査を並行して行い、そのあと実際のアプリでFeature Mapの全機能を確認します。長く動くUIやサーバーは、調整役が一つのインスタンスを順に操作します。短命のCLIなら、生成されたLaunch手順に沿って実行ごとに独立したセッションを使います。

ソースを読む作業は分担し、同じアプリへの書き込み操作は調整する。この分け方が、誤操作や状態の奪い合いを防ぎます。

結果は三種類です。

結果 意味
clean ソースと実動作の確認が完了し、修正不要
changed 証明できた検証スキル・操作スクリプト・地図の修正を一つのPRにする
blocked 確認や安全な修正完了を妨げる具体的な事情がある

この作業で変更するのは、検証スキル自身のディレクトリです。アプリ本体の不具合は、手順書の記述を変えて隠さず、製品側の問題として報告します。 本体の修正は別の作業です。保守スキルの定義

実行頻度は開発の変化量で決めます。毎日画面が変わるなら頻繁に、安定しているなら機能変更時に行う、といった運用が考えられます。現在の生成スキルは、保守を案内しますが、定期実行を勝手に設定するものではありません。

「毎日回す」とチャットに書いた場合も、実際にスケジュール機能へ登録されたか、次回実行が存在するかを確認します。会話の約束だけで、翌日の実行が始まるとは限りません。

8. 既存コードを理解する四つの入口

仕事でpstackを使うと、新規開発以上に「前からあるコードを理解する」時間が重要になります。

そのときは、知りたいことによってスキルを選びます。

スキル 答える問い
/how 今、どう動いているか
/why なぜ、その設計・実装になったのか
/teach 自分が理解できる形で説明してほしい
/recall 過去の関連作業の文脈を取り戻したい

/how：実際の処理を辿る

入力・表示例
/how ログインしてからホーム画面が表示されるまでの流れを説明してください。
認証、ユーザー情報の取得、画面表示の順序を知りたいです。

返ってくる説明では、入口と出口、その間のデータの流れに注目します。複雑な対象では複数の調査役に分担し、小さい問いなら必要なコードを直接読んで説明する定義です。

/why：設計の理由を証拠から調べる

入力・表示例
/why 通知の再試行回数が5回なのはなぜですか。
過去の不具合や設計上の理由があるか、履歴から調べてください。

Git履歴や、接続されているIssue管理、設計資料、チャットなどを手がかりにします。ただし、pstackを追加しただけでSlackやNotionの情報を読めるわけではありません。利用できる連携と権限の範囲で調査します。

理由を記録した資料が見つからなければ、「理由は確認できない」も有用な結果です。もっともらしい経緯を作って埋めるより、事実と推測が分かれているほうが、次の判断に使えます。

/teach：設計判断を自分の言葉にする

入力・表示例
/teach 今回、キャッシュを追加せずにクエリを変更した理由を説明してください。
両案の違いと、採用案が今回の問題を解決すると言える根拠を知りたいです。

要約だけではわからないときに使います。実装の仕組みと理由を組み合わせ、人間が判断できる説明にするためのスキルです。

/recall：昨日の続きを始める

入力・表示例
/recall 先週のCSVインポート改善について、決まったこと、残った問題、次の作業を整理してください。

これは、アクセスできる過去の会話と共有記録から文脈を回収するものです。全アプリ、全アカウントの履歴を自動的に共有する仕組みではありません。

特定のブランチ上の作業を引き継ぐなら、履歴の検索に加えて現在の状態も確認させます。

入力・表示例
/poteto-mode このブランチの作業を引き継いでください。
引き継ぎメモ、判断ログ、差分を読み、完了済みと未完了を分けてください。
以前の「検証済み」という報告が今のコードにも当てはまるか確認してから続けてください。

これがSession pickupの使い方です。過去の説明を読み直すだけでなく、今のコードに照らして再開地点を決めます。理解と引き継ぎの公式ガイド

9. 大きな変更は、設計を実物で比較する

小さなオプション追加と、認証方式の変更では、必要な設計の深さが違います。pstackには、後から戻しにくい判断に時間を使うための仕組みがあります。

/architect：使う側のコードから考える

新しい内部ライブラリやサービス境界を設計するとき、実装の都合から始めると、利用側が複雑になりがちです。

入力・表示例
/architect with checkpoint.
複数の画面から使うCSVインポート機能を設計してください。
利用側がどう呼び出すかを先に示し、そのあと型とモジュールの境界を提案してください。
既存の実装を確認し、設計案を見せたところで止まってください。

このように、まず呼び出し側の使い方を見れば、「このAPIは本当にわかりやすいか」を実装前に判断できます。

設計書だけでは決まらない問題は、小さな試作品で測ります。たとえば、二つの検索方式の応答時間や、テーブルとカードのどちらが一覧を見やすいかは、動くものを比べるほうが早い場合があります。architectの定義

/arena：同じ課題を、複数の独立した案で解く

入力・表示例
/arena CSVインポートのエラー表示を3案比較してください。
同じ不正データを使い、利用者が直すべき行を特定できるか評価してください。
各案は独立した場所に作り、比較結果と推奨案を示してください。
今回は試作の比較までで、本体への取り込みはしないでください。

Arenaでは複数の担当に同じ課題を渡し、独立した候補を作ります。そのあと別の評価役と調整役が比較し、必要なら良い部分を組み合わせます。

多数決で勝った案が必ず正しいわけではありません。「同じ入力に対してどう動いたか」「何が複雑になるか」という評価基準が必要です。違うモデル系列の評価役を使えるかどうかも、モデル設定に依存します。arenaの定義

/swarm：違う範囲を分担して調べる

Arenaと似て見えますが、目的が違います。

入力・表示例
/swarm packages/ 配下の各パッケージを調べてください。
1担当につき1パッケージで、READMEの起動手順が実際に通るか確認します。
製品コードは変更せず、結果を一つの表にまとめてください。
Arena Swarm
渡す仕事 同じ課題を複数の担当へ 異なる範囲や検証条件を分担
欲しい成果 比較して選び、統合した案 各範囲の結果を集約した報告
向いている例 API設計を3案比較 10パッケージの起動確認

Swarmには条件を宣言した競争実行もありますが、初心者は「調べる範囲を分ける道具」と覚えると使い分けやすいでしょう。swarmの定義

/interrogate：別の視点から変更を疑う

入力・表示例
/interrogate このブランチの変更をレビューしてください。
実際の不具合、既存動作の退行、データの不整合を優先してください。
まず指摘と根拠を示し、コードは変更しないでください。

Interrogateは複数のレビュー結果をまとめ、対処すべきもの、検討するもの、参考情報、棄却するものに分類します。指摘された数をそのまま品質スコアにしないことが重要です。

たとえば「この条件で二重保存になる」という指摘は、該当する実行経路で再現できるか確認します。「念のためチェックを増やすべき」という指摘は、既存の境界で保証済みかもしれません。

指摘をすべて受け入れるのではなく、採用・棄却のどちらにも理由を持つためのレビューです。interrogateの定義

10. 不具合修正と性能改善で、頼み方を変える

不具合は「再現した条件」を最後まで持ち続ける

入力・表示例
/poteto-mode 設定を保存してすぐ再読み込みすると、変更が消えることがあります。
まず実際の画面で再現し、操作順と保存結果を記録してください。
原因を絞り込んでから修正し、同じ操作で保存が維持されることを確認してください。

最初に再現した操作と、修正後の確認操作が違うと、直ったかどうか判断できません。エラーが消えたとしても、保存自体をしなくなっただけかもしれません。

安価に自動テストを書ける問題なら、修正前に失敗し、修正後に通るテストを残します。pstackには /tdd もあります。ただし、巨大なモックを作って現実から離れたテストを増やすより、利用者と同じ経路で確認するほうが適切なケースもあります。不具合修正プレイブック

再現できなかった場合は、そのまま「修正済み」と扱わないでください。試した条件、観測できたこと、残った条件を報告させます。

性能は「速くなった気がする」から離れる

入力・表示例
/poteto-mode 一覧の初回表示を改善してください。
まず現在の処理時間とトレースを取り、時間を使っている箇所を特定してください。
同じデータ量、同じ環境、同じ操作で変更前後を比較してください。
速くならなかった変更は残さず、採用した変更と測定結果を示してください。

ここでのトレースは、どの処理にどれだけ時間がかかったかを記録したものです。エージェントにコードを読ませて推測だけで最適化させるのではなく、計測から仮説を作ります。

測定値には、対象の操作、入力データ、単位を添えます。開発モードと本番ビルド、初回とキャッシュ済みの読み込みを混ぜて比較してはいけません。

一つの数値を継続的に改善したい場合は、Hillclimbのプレイブックもあります。「一定の入力で処理時間を目標以内へ縮める」のように、測れる目標を渡します。試行を重ねても結果が伸びないときに、成功条件をこっそり緩めないことが大切です。性能改善プレイブック・Hillclimb

11. PRを作る、マージ可能にする、マージする

本格運用では、この三つを区別してください。

PRはPull Requestの略です。ブランチ上の変更を、ほかの人が確認し、取り込める形で提示するものです。マージは、その変更を取り込む操作です。

入力・表示例
変更と検証
    ↓
PRを作成
    ↓
レビュー・CI・取り込み条件を確認
    ↓
マージ可能な状態
    ↓
マージ
    ↓
プロジェクトの配備手順と、本番での確認

PRを作る

練習用のローカルプロジェクトと違い、PRを作るには対象のリモートリポジトリと、操作できる認証環境が必要です。GitHubの場合、公式プレイブックの基本経路はGitHub CLIの gh です。Origin CLIがあり対象を解決できる場合は、そちらを使う定義もあります。

最初に、対象を確認させます。

GitHub CLIをまだ用意していない場合は、公式の導入案内 に沿ってインストールします。次に、ターミナルでログインします。

ターミナルで実行
gh auth login

作業対象のリポジトリで、次を実行します。

ターミナルで実行
git remote -v
gh repo view --json nameWithOwner,defaultBranchRef

表示された所有者・リポジトリ名と取り込み先を確認します。ログインできても、そのリポジトリを操作する権限があるとは限りません。権限エラーが出る場合は、対象を操作できるアカウントや連携設定を先に整えます。教材のようにリモートを登録していないローカルリポジトリでは、ここから先のPR操作はまだ行えません。GitHub CLIの認証手順

入力・表示例
/poteto-mode この変更をPRにする前に、対象リポジトリ、現在のブランチ、
取り込み先ブランチ、含まれる差分、認証状態を確認してください。
まだpushやPR作成はせず、確認結果を示してください。

対象が正しいことを確認できたら、作成を依頼します。

入力・表示例
/poteto-mode 確認した変更をPRにしてください。
小さく順序のわかるcommitに整理し、何を変え、どう動作確認したかを本文に書いてください。
レビュー可能な通常PRとして作成し、マージはしないでください。

現在のOpening a PRプレイブックは、通常のレビュー可能なPRを作り、PRを開いただけでBabysitを始めない定義です。本文では目的、影響、トレードオフ、検証結果を簡潔に示します。PR作成プレイブック

Babysitでマージ可能な状態にする

CIとは、リポジトリ側で自動実行されるテストやビルドなどです。PRを作ったあと、CIが失敗したりレビューが追加されたりするので、その追従を依頼します。

入力・表示例
/poteto-mode このPRをbabysitしてください。
レビューの指摘とCIを確認し、必要な修正をしてマージ可能な状態にしてください。
マージと自動マージの設定は行わないでください。

現在のBabysitには、通常の追従、背景での対応、レビューコメントのみ、状態確認のみというモードがあります。単に現状を知りたいときは、軽く頼めます。

入力・表示例
/poteto-mode このPRの状態だけ確認してください。
残っている指摘、CI、マージを妨げる条件を報告し、変更はしないでください。

Babysitはマージを行いません。 また、現行定義ではスタックの付け替えやrebaseを自分で行わず、競合があれば所有者側の調整が必要だと報告します。一般的な「CIが緑になるまで何でも直すツール」という説明より、役割が厳密です。Babysitの定義

Shippingで、独立した検証を経てマージする

実際に取り込む場合は、対象を特定して依頼します。

入力・表示例
/poteto-mode 確認済みのこのPRをshipしてください。
変更を書いた担当とは別の担当が実際の挙動を検証し、
その検証が現在の差分に対応していることを確認してからマージしてください。

現行のShippingは、PRごとに独立したCursor cloud agentが実際の挙動を確認し、その結果に基づいてマージする手順です。Cloud Agentsを使える環境や、対象を実行・操作できる仕組みが前提になります。

ここまで未設定の場合は、「Shippingを呼べば全部揃う」と考えず、まずクラウド側で検証が成立するよう準備します。クラウドを使わない運用なら、PRをマージ可能にしたあと、人間が自分の検証と取り込み手順で扱う選択もできます。Shippingの定義

依存するPRは、下から順に扱う

たとえば次の関係を考えます。

入力・表示例
main
  └─ PR A：データ構造を追加
       └─ PR B：そのデータを使うAPI
            └─ PR C：APIを使う画面

これがPRのスタックです。Cだけ確認済みでも、その前提であるBが未検証なら、Cまで取り込んでよいとは言えません。

Shippingは、最下段から連続して検証済みの範囲だけを対象にします。また、検証後に差分が変わったら、古い検証結果をそのまま使わないよう確認します。

初心者の段階では、まず独立した一つのPRを最後まで進めてから、スタックへ広げると理解しやすくなります。

マージ済みと、本番で動作確認済みは別

PRがマージされても、配備が失敗したり、本番の環境変数が不足したりすることがあります。

pstackのShippingを、本番監視サービスや汎用の配備設定ツールとして扱わないでください。自分のプロジェクトのCI/CDと配備手順に合わせて、マージ後の確認を定めます。

入力・表示例
/poteto-mode 今回のマージが本番へ反映されたか確認してください。
対象の配備と実行中の版を照合し、テスト用アカウントで変更した経路を確認してください。
配備成功と、アプリの動作確認を分けて報告してください。
本番データを書き換える操作は、実行前に対象と影響を示してください。

「マージ済み」「配備済み」「本番の対象機能を確認済み」の三つを区別すると、作業完了の判断が明確になります。

12. 長時間任せるときは、終わり方を先に決める

一件の修正を任せられるようになったら、夜間の移行作業などにも使えます。ただし、「4時間頑張って」では、何をもって成功とするか決まりません。

13. 複数エージェントとCloud Agentsへ広げる

並列化する前に、まず一体が自分の変更を確実に検証できる状態を作ります。起動方法が不明なエージェントを10体に増やしても、調査の重複が10倍になるだけです。

並列化では、ファイル以外の共有状態も分ける

別ブランチにしただけでは、同じ開発用データベースを書き換える可能性があります。

共有すると衝突しやすいもの 分け方の例
ソースの作業フォルダ worktreeを分ける
開発サーバー ポートを分ける
データベース テスト用DB・スキーマ・データを分ける
ブラウザ プロファイルやセッションを分ける
出力ファイル 担当・試行ごとの保存先を使う

複数人が同じアプリ画面を同時に操作すると、片方が開いた画面を別の担当が閉じることもあります。独立した環境を用意できない場合は、操作を一人にまとめます。

ローカルのworktreeとCloud Agentsを使い分ける

Lauren Tanの解説では大規模な並列化にCloud Agentsを推しています。一方、現在の公式ガイドにはローカルworktreeの活用も書かれています。「worktreeは常に禁止」と一般化する必要はありません。

方法 向いている状況 事前に確認すること
ローカルworktree 手元で動くアプリ、少数の並行作業 CPU・メモリ・ディスク、ポートやデータの分離
Cloud Agents 手元のPCに依存させない作業、複数の独立した実行環境 リポジトリ接続、起動環境、秘密情報、外部接続、利用費用

Cloud Agentsはクラウドの独立したVMで開発環境を動かします。手元のPCがインターネットにつながっていなくても進められる一方、手元にしかないアプリや認証、ファイルへそのままアクセスできるわけではありません。CursorのCloud Agents

クラウドでの最初の一件

次の順序で整えると、どこが足りないかを切り分けやすくなります。

  1. Cursor側でソース管理との接続と対象リポジトリの権限を確認する。
  2. Cloud Agent用の環境を設定し、依存関係を入れてアプリを起動できるようにする。
  3. 開発・検証に必要な秘密情報を、指定されたSecretsの仕組みで渡す。
  4. pstackとプロジェクトの検証スキルが、クラウド側でも利用できるか確認する。
  5. まず小さな一件で起動、操作、証拠保存まで試す。

環境設定にはエージェントによるセットアップ、スナップショット、.cursor/environment.json でのDockerfile指定などの経路があります。具体的な設定は、Cloud Environment Setup に従ってください。

手元の ~/.cursor/rules/pstack-models.mdc が、そのままクラウドへコピーされるとは仮定しないでください。クラウド側で見えるモデルと設定を確認します。プロジェクトに置いた検証スキルも、commit・pushされていなければ新しいクラウド環境には届きません。

入力・表示例
/poteto-mode このクラウド環境で、アプリの起動と検証手順が成立するか確認してください。
製品コードは変更せず、現在の検証スキルに従って一つの機能を操作してください。
使った環境、実行コマンド、結果、保存した証拠を示してください。
手元だけにある設定が必要なら、その不足を明示してください。

一晩に複数の仕事を任せる三つの方法

現在のpstackには、規模に応じたプレイブックがあります。

方法 使いどころ マージの扱い
Autopilot-stack 関係する変更を一本のPRチェーンに揃え、人間が確認したい スタックを準備し、マージしない
Autopilot-full 独立した変更群を、それぞれ完了まで進めたい 明示された権限と独立検証の条件でマージまで進む
Orchestrate 数日規模で複数の作業を継続管理したい 調整役がプログラム全体を管理する

これらは単に /swarm で数人に分けるより重い仕組みです。担当、PR、検証結果、進行状況を追跡します。一件の作業で済むなら、まず前章の長時間実行で十分です。Autopilot-stack・Autopilot-full・Orchestrate

実行方法を理解する段階では、次のように方針の提示だけを依頼できます。

入力・表示例
/poteto-mode この三つの変更をautopilot-stackで進める場合の方針を示してください。
各変更の依存関係、担当、検証方法、最終的なPRチェーンを説明してください。
今は方針の提示だけで、実行開始は私のGOを待ってください。

これで、どこまで任せるのかを具体的に判断できます。

原因と、次回同じところで止まらないための改善案をまとめてください。
ルールを増やすだけでなく、起動確認や準備スクリプトで解決できるか検討してください。

pstackの /reflect は、単なる週報生成ではありません。作業を振り返り、今後のスキル改善につながる提案を作ります。現在の公式ガイドでは、提案を整理し、スキルを変更する前に承認を待つ流れです。

たとえば「説明は日本語」「性能改善では必ず前後の数値を比較」「取り込み前に一度確認」といった傾向です。pstackを基礎として使いながら、自分向けの入口を追加できます。

最初から行うより、いくつかの仕事を終え、自分の好みが履歴に表れてからのほうが判断しやすくなります。提案されたルールが、偶然の一回の依頼なのか、長く使いたい方針なのかは、自分でも確認してください。automate-meの定義

15. 毎日の運用に落とし込む

ここまでの機能を全部毎日使う必要はありません。普段の仕事には、次の流れを出発点にできます。これは公式の必須日課ではなく、本記事の運用例です。

作業開始時

昨日からの続きなら、/recall で文脈を戻し、ブランチと未完了事項を確認します。新規作業なら /poteto-mode に目的、制約、完了条件を渡します。

実装中

変更前の症状や出力を記録します。設計で迷う場合は試作や /architect を使い、小さな単位で変更と検証を繰り返します。

完了前

実際の利用経路を確認します。影響の大きい変更なら /interrogate や /blast-radius で、隣接する経路への影響を調べます。PRを作る場合は、検証結果を本文に残します。

作業後

繰り返しそうな遠回りがあれば /reflect。アプリの画面や操作が変わったなら、検証スキルとFeature Mapの更新も確認します。

進歩は何で測るか

PR数だけでは、仕事が良くなったか判断できません。次のような指標を、自分の課題に合わせて選びます。

  • 問題を報告してから、再現できるまでの時間。
  • PRを作ってから、必要な修正が終わるまでの時間。
  • AIの作業後に、人間がやり直した回数。
  • 検証できずに終わった作業の割合。
  • 利用者に影響する不具合や手戻り。
  • 一件の完了に使った費用。

最初は一、二個で十分です。「AIが長く動いた」より、「同じ品質の仕事を、少ない手戻りで終えられた」を確認しましょう。

16. よくあるつまずきと対処

コマンドが候補に出ない

まず、操作しているのがCursorのチャットであること、pstackが追加されていることを確認します。次に、新しいチャットで再確認します。

/deslop や control-ui は cursor-team-kit 側の機能です。生成された検証スキルは、実際の name を確認してください。別プロジェクトのpstackの記事からコマンドを混ぜていないかも見直します。

モデルが起動しない

/setup-pstack を再実行し、現在使えるモデルだけで設定し直します。ブログや古い設定ファイルに載っているモデル名が、自分のアカウントでも使えるとは限りません。

「検証済み」と言うが、証拠がない

入力・表示例
実際に実行したコマンドか操作と、その結果を示してください。
未実行の確認は未実行と分けてください。
保存した証拠が現在も読めるか確認してください。

スクリーンショットがある場合も、対象の画面か、操作の結果が写っているかを確認します。保存されたことの証明に、保存前の画面だけを使わないようにします。

調査だけ頼んだのに、修正へ進む

入力・表示例
目的は調査です。修正はまだ依頼していません。
今わかった事実、推測、追加で必要な観測を分けて、変更せずに報告してください。

前の作業から話題を変える場合は、new task も添えます。

設計の議論が長く、判断がつかない

入力・表示例
未解決の問いを一つ選び、判断できる最小の試作品か測定を行ってください。
結果を見てから設計を決めたいです。

たとえば「大量データで重いかもしれない」なら、対象量のデータで測ります。実験で決まる問題を、文章だけで延々と検討しないための切り替えです。

並列作業でファイルや状態がぶつかる

作業フォルダだけでなく、DB、ポート、ブラウザ、出力先を確認します。分離できないものは一人に操作をまとめます。「もう少し注意して」より、共有状態を減らすほうが再発を防げます。

PRが緑なのにBabysitが完了しない

テスト結果の一覧以外に、取り込み先との競合、未解決のレビュー、必須承認などが残っていないか確認します。現在のBabysitは、単なる緑のチェック一覧ではなく、利用しているホスト側のマージ可能性を見ます。

本番へ出すつもりがない

作業の最初に「ローカルの修正まで」「通常PRの作成まで」「マージ可能にするまで」と明記します。ship、land、merge は、取り込みを依頼する言葉として区別します。

動画がほしいのに、取れない

対象の環境に録画可能な操作ツールが必要です。動画を生成できない場合、取れたふりをさせず、何が足りないかを示してもらいます。CLIの変更なら、動画より実行ログと終了コード、出力ファイルの内容のほうが適切な証拠になることもあります。

更新後に挙動が変わった

利用中のプラグイン版、モデル設定、補助プラグインの有無を記録します。更新後は、本番作業の前に、小さな既知のタスクでスキル認識と検証経路を試します。コマンド名や手順に迷ったら、利用中の版の SKILL.md を確認します。

公式サイトの main は変化します。本記事の参照先は、再確認できるよう主要部分を調査時のコミットへ固定しています。
