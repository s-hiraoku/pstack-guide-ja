前回の投稿では、エージェントで私がやるすべての土台が検証であること、自分の検証スキルを作り始める方法を見せました。要点は、エージェントが自分の作業を確かめられないなら、他は何も意味がない、ということです。あなたがボトルネックのままになり、一日中エージェントの世話をすることになります。

検証が動くようになったあとの次の問いは、実際に何を作るかをどう決めるかです。

この投稿では、pstack で調査、計画、プロトタイピング、アーキテクチャをどう進めるかを歩きます。月に数千本の PR を本番へ出しながら、コード品質を極端に高く保つ、まさにその手順です。

自分より賢い相手を監督する技術

2024 年の昔は、システムに何か変更を入れるには、まず十分読んで、何が起きているかのメンタルモデルを作る必要がありました。コードベースの大きさと複雑さ次第で、何時間、ときには何日、何か月かかることもありました。小さな変更なら、小さなサブシステムの局所的な理解で足りることもありました。中核をリファクタするなら、正しく効果的にやるために、全体がどう動くかのメンタルモデルがほぼ必要でした。

エージェントはこの障壁を明らかに取り除きます。コードをどれだけ知っているかに関係なく、エージェントに頼めば変更できます。しかしコードとユーザー体験の品質を高く保つのは、まだ難しいです。特に、何を見て何を聞くべきかを知っている領域の専門家でなければそうです。

フロンティアモデルは非常に有能になりましたが、私が絶えず見る失敗モードはまだ 2 つあります。

  • 指定が不足している、または悪いので、あなたの意図を完全に理解できない。
  • 作業を正しくやるための文脈が足りない。

この二つはつながっています。エージェントをうまく使うことは、高品質な文脈でエージェントのコンテキストウィンドウをどれだけ準備できるかに尽きます。これをせずに動くコードは書けます。しかし、高品質な仕事に必要なものをすべて渡す作業をしたときのほうが、結果と品質はずっと良いです。

エージェント自身の言葉で

フロンティアモデルは非常に有能なコーダーです。古いモデルでは、やってほしいことを非常に具体的に指示し、ほとんどマイクロマネジメントしていました。最新のモデルは、あなたや私より上手にコードを書けます。だから、達成してほしいことは伝えつつ、自分が思いつかないやり方で解く自由も渡す、というバランスを取りたいのです。

これが、自分より賢い相手を監督する技術です。自分で書いていないコードベースの上で、人間がコードベース全体のメンタルモデルを頭に収められなくなった場所で、それをやります。

私が好む技法の一つが、間接的なプロンプトです。欲しいものを正確に伝える代わりに、エージェント自身の言葉で引き出すようにします。

たとえば Slack で問題が報告されたとき、私はしばしば、何かをする前にスレッドを読み、問題をエージェント自身の言葉で言い直させます。

たとえば次のように言います。

text
/poteto-mode read this slack thread. restate in your own words and in plain english what you think the underlying issue is

これで三つのことが起きます。

第一に、騒がしい会話を、構造化された問題文へ圧縮させます。第二に、誤解をすぐ捕まえられます。スレッドの赤いニシンに固着したら、コードを書き始める前にすぐ直せます。

第三に、自分の前提や仮説を述べて、誤った道へ連れて行ったり、エージェントが本来達成できたことを制限したりせずに済みます。その前提が間違っているかもしれないからです。

メンタルモデルを組み立てる

自分より賢い相手と働くとき、あなたが理解できる形で言い直させることは重要です。それが `/teach` の着想です。エージェントが直観的なやり方で説明するためのスキルです。エージェントがしていることが自分に意味をなすかを確かめたいときに使います。

内部では、/teach は `/how` と `/why` を呼び出します。

/how は実行時の仕組みを辿ります。/how を聞くと、エージェントはサブシステムの複雑さを見ます。複数ディレクトリやサービスにまたがるなら、Grok のような速くて効率的なモデルで、並列の explorer エージェントを spawn します。

text
/how is virtualization implemented?

/why は動機と意図を調べます。コードは何が起きるかを伝えます。なぜそう書いたかは、めったに伝えません。/why を走らせると、pstack は複数の出典を並列に調べます。Git 履歴と PR レビューコメント、Linear チケット、Notion の設計ドキュメント、Slack の会話、Datadog のモニタ、Sentry のエラー、コードの系譜、分析ウェアハウスのイベントです。

text
/why are we still stuck an old version of node.js?

エージェントに何か言い直させて、理解と信頼を上げたいときは /teach を使います。

text
/teach me why you implemented it this way and not <other way>. what were the tradeoffs you made and why?

実務では、/teach の調査は人間だけでなくエージェントにも役立つとわかりました。最新のフロンティアモデルでも（ハーネスの質にも依りますが）、一般に、データや、仕組みのメンタルモデルを作るのに必要なコードを読まずに、自信満々に述べることが多いです。だから、何をしようとしているか、なぜかを教える行為は、エージェント自身にも役立ちます。

履歴から学ぶ

私のプロジェクトの多くは、複数の会話にまたがります。たとえば数か月前、Cursor で報告されていた仮想化の不具合と perf の問題を直していました。新しいチャットを始めるたびに、似た問題を解いていたときの豊かな文脈を、ほぼ一から作り直す必要がありました。

気づいたのは、過去のトランスクリプトが豊かな文脈の金鉱だということです。pstack には `/recall` があり、チャット履歴から最近の文脈を引きます。新しいエージェントでも、良い状態に戻るための正しい文脈を持てます。

text
/recall the work i did yesterday on virtualization and then read this bug report on slack

/teach、/recall、/how、/why で、自分のコードベースのメンタルモデルを最新に保ち、覚えやすく理解しやすい形へ圧縮しています。エージェントにも役立ちます。

逆算して考える

問題がわかったら、解をどう指定しますか。

計画モードを持つハーネスの多くは、実装の詳細を過剰に指定し、それ以外を過少に指定すると私は思っています。だから pstack では、冗談めかして「計画は信じていない」と書きました。実際は計画します。ただしコードを通して計画します。

共有コードや、他の人が使うパッケージを作る種類の仕事では、readme driven development を強く信じています。馴染みがなければ、昔よく使われた開発の技法で、まず readme を書きます。開発者体験の帽子を被り、仮想のユーザー向けに API を先に書き、そこから実装とアーキテクチャへ逆算します。

たとえば社内のデスクトップアプリ向けクライアントフレームワーク Dune を作ったとき、まずチュートリアルを書き、それでアプリを作る感覚を理解しようとしました。少なくともそうしようとしました。エージェントから良くて読めるものを出すのは本当に苦労しました。だから先に刃を研ぐ時間を取り、`/technical-writing` スキルを作りました。

/technical-writing なしの最初の readme は、目的が混ざっていて読むのが苦痛でした。チュートリアル、ハウツー、アーキテクチャの説明、API リファレンスを同じ文書にしようとし、いつもの AI のスロップと気どった散文で書かれていました。

/technical-writing は Diátaxis フレームワークを使い、文書を四つのモードに分けます。

  • Tutorial: やって学ぶ。新参者が一連の手順で、目に見えるものを作る授業です。
  • How-to guide: 経験者向けに、具体的で現実の問題を解く手順です。
  • Reference: 機械、API、設定フラグの、乾いて完全で権威ある技術記述です。
  • Explanation: 背景、設計判断、トレードオフを照らし、明らかにする高いレベルの議論です。

`/unslop` も使うので、非常に読みやすい文書になります。

この書き方で計画すると、エージェントが自分の作業を照合できる具体的な目標ができます。エージェントが何を作るかも、ずっと理解しやすくなります。

設計の段階では、pstack の多くのスキルがここで合成されます。たとえば次です。

text
(1) /recall my work fixing virtualization bugs and perf issues from the past 7 days. use /how and /why to understand how our current virtualization implementation works.

(2) then use /poteto-mode planning and /technical-writing to come up with a new virtualization engine that categorically eliminates flickering and jittering. let's start by writing a tutorial on how i would use this new package to virtualize a React app

(3) after you write the plan, /teach me and prove to me why this new approach is superior to our current engine

この技法の要点は、興味深く豊かな文脈を引き出し、エージェントが問題をあなたと同じように見られるようにすることです。小さな切片としてだけではなく、です。

  • プロンプトの第一部は、アプリで仮想化がどう実装されているかについて、過去と現在の関連文脈を思い出します。
  • 第二部は、以前直した不具合などの文脈を使い、それらの問題をまるごと消す新しい設計を考えさせます。
  • 最後は、この新しいパッケージが優れていることを証明させます。ここで、検証スキルのような高品質な道具が重要になります。

百回測って、一度で切る

計画するとき、よく見る間違いは二つです。

  • エージェントの最初の設計を受け入れる。
  • 経験的な証拠なしに計画を煮込みすぎる。

人間がコードを書いていたころは、設計ドキュメントでよく協働していました。高いレベルのアーキテクチャ、検討した代替、トレードオフ、珍しい実装メモを話す文書です。落ち着いた設計に至るまで、何度も改稿するのが普通でした。

エージェントでは設計ドキュメントの儀式は飛ばせますが、エージェントが最初に返したものを受け入れてしまう誤りをよく見ます。pstack では、「二度測って一度切る」を極限まで持っていけます。並列エージェントを使います。

それをやるのが、プロトタイピングのプレイブックです。

pstack では、プレイブックはスキルではなく、/poteto-mode の中の参照ファイルです。作業の種類に応じて条件付きで読み込まれます。トークン効率のためです。0.15.0 時点で 23 のプレイブックがあり、それぞれ私が作業するときの手順が入っています。

スキルと違い、プレイブックは /poteto-mode の一部としてエージェントが自動で使います。たとえば次です。

text
/poteto-mode prototype a few options for the new dropdown menu
/poteto-mode fix this bug
/poteto-mode eval this skill change

プロトタイピングは、私が一番好きな pstack のプレイブックの一つです。一つの目標に何度も当たり、最良の選択肢をエージェントに考えさせます。見た目のプロトタイプだけでなく、機能や不具合修正などの違う解を試作するときにも使えます。

text
/poteto-mode prototype a few options for <feature request>. use /control-app* and take videos/screenshots for me to review and choose from

注: /control-app は第1部で作った検証スキルです。

見た目の変更を試作するとき、エージェントはアプリの中か、作業用ディレクトリに捨てるスケッチを作ります。UI の操作を試すなら、2 つまたは 3 つの変異を簡単な切替の後ろに置きます。それから /control-app で操作し、各変異のスクリーンショットを撮り、実際のタイミングやレイアウトを測ります。

プロトタイピングは、コードでやる計画です。エージェントが問題空間を探る自由を持ち、自分では思いつかないもので驚かせる余地を与えます。プロトタイプは、私の入力を待たずに、経験的な証拠で自分の問いに答えられます。

より大きな変更を設計する

エージェントの時代のエンジニアとして、私が時間を使うべきなのはアーキテクチャ、正しいデータ構造の選択、作るシステム同士がどう協働するかです。実装の詳細はエージェントが埋めます。

pstack が同梱するもう一つの有用なスキルが `/architect` です。設計を、区切られた厳密な段階にします。

  • Ground the problem。エージェントは影響するシステムに /how と /why を走らせ、既存の所有と制約の正確なメンタルモデルを作ります。
  • Sketch。エージェントはアーキテクチャの arena に入ります。独立した候補 runner を並列に spawn し、しばしば違うモデル家系にまたがります。各 runner は grounding の brief を受け、完全な設計パッケージを書きます。呼び出し側の usage sketch、中核の型定義、公開関数のシグネチャ、短い根拠です。ふつうは、呼び出し側をどう見せたいかから導いた型シグネチャだけをスケッチします。各 runner は interface depth を評価し、弱いモデルでの失敗モードを見、設計の赤い旗のカタログで検査しなければなりません。
  • Cross-judge and Synthesize。メインエージェントと違うモデルの cross-judge エージェントが、厳しいルーブリックで候補を評価します。
  • Implement against the sketch。エージェントはスケッチの仮本体を本物の論理に置き換えます。実装中に、想定外の引数や追加状態が必要だとわかったら、その食い違いを表に出します。
  • Scrap when the design is wrong。実装中にスケッチが間違っていたとわかったら、全部捨ててやり直します。

要点は、エージェントに自己完結した小さなループを渡すことです。違うモデル家系からの複数の競合設計を一つの最適なやり方へ合成し、厳密であり、経験的な証明でアーキテクチャが間違っていたら捨てることを恐れない。同じ回避が無関係な呼び出し側に何度も出る、型が any や強制キャストのような逃げ穴を必要とする、それがアーキテクチャが間違っている経験的な証明です。

text
/architect this new <feature request>

大きな教訓は、/poteto-mode のプロトタイピングと /architect で、コードを使って計画するほうがはるかに効果的だということです。

抽象計画を敵対的にレビューしない理由も同じです。エージェントは理論上のリスクを幻覚し始め、起きない問題を守るための複雑なエッジケースを発明します。まだ抽象な計画を煮込みすぎないでください。開いた問いは、プロトタイピングと自分の作業の検証で、エージェントに答えさせてください。

それでも計画ドキュメントが欲しい

pstack に計画スキルはありませんが、複数フェーズの計画プレイブックは同梱しています。気に入った設計が出たあと、戦術的な実行計画を作るために使います。

text
/poteto-mode turn this design into a plan

計画のすべてのタスクは、証明と検証を軸に組まれます。プレイブックは、テストだけでは検証として足りないとエージェントに伝えます。コードを実際に走らせ、動くことを確かめたときだけ、検証済みです。

すべての計画は、構造と書式を検証する自動スクリプトで検査されます。承認されたら、項目ごとに実行します。各 PR は小さく、自己完結し、レビューしやすいです。

本当に大きなプロジェクト（1 週間かかるようなもの）では、進行中の作業を他のエージェントに知らせるため、計画を一時的にコードベースへコミットすることがあります。終わったら消します。コードベースを混乱した状態に残したくないからです。計画を永久に残す価値は、私は感じていません。

実際のワークフロー

これらの部品がどうはまるかを見るために、私がこれらの手順をどうプロンプトするか、具体例を三つ、実際には四つ歩きます。

例1: 曖昧な不具合を調べる

本番で問題が出て、根本原因がはっきりしないときです。

text
/poteto-mode investigate why background workers periodically fail with timeout errors. give me a breakdown of what we know, what data you used, and your best hypotheses.

エージェントはコードを探り、メトリクスと過去のコミットを並列に見、問題がどこにありそうかの、いちばん良い推測を返します。

例2: 新しいサービス境界を設計する

他モジュールが依存する新しいサブシステムを入れるときです。

text
/poteto-mode we need to add rate limiting for external webhooks. /architect this first, and answer any open questions with prototypes. let me review before proceeding.

エージェントは既存の webhook アーキテクチャを接地し、複数モデルで競合する設計 runner を回し、捨てるプロトタイプでベンチし、きれいで検証済みのインタフェースを出します。

例3: 複数 PR の移行を実行する

多くのファイルにまたがる複雑なリファクタを実行するときです。

text
/poteto-mode create a plan to migrate our entire UI library to StyleX. break the migration into small, verifiable PRs. each PR must have its visual regression tests and live verification steps. i want the final result to be 100% identical compared to the original - bugs included

エージェントは作業を独立した段階に分け、監査できるチェックリストを書き、各単位を作り、確かめ、安全に入れられるようにします。

例4: Slack で人が報告したものを直す

社内の issue やフィードバックチャネルの Slack で私を見たことがあれば、次の定番を見たことがあるでしょう。

text
# thread already has sufficient context
/poteto-mode do it

/poteto-mode repro this with /control-app. if it repros on main, fix it and show me a video as proof

ここで話したスキルの多くは、すでに /poteto-mode が自動で使います。ほとんどの場合は /poteto-mode だけでよく、あとは自分の生活に戻ればよいのです。

計画の技術

Plan Mode は、エージェントが正しいことをすると自分を納得させる手段として使われがちです。実際には、抽象計画は進捗の錯覚しか与えません。長く厚い計画は、あなたとエージェントがとても生産的だったように見えます。中身はたぶん足りません。

pstack は、徹底した調査、経験的な証拠、厳密な検証を組み合わせる道具を渡します。こう計画すると、エージェントとのエンジニアリングは賭けのように感じなくなります。予測でき、繰り返せます。
